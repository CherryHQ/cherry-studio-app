# Gmail plugin authorization

The plugin uses the official Gmail API with only `gmail.readonly`. It searches messages and
threads, reads decoded message text and attachment metadata, lists labels, and verifies the mailbox
identity. Summaries are generated by the conversation model. It does not send mail, create drafts,
change labels, mark mail read, delete mail, or download attachments.

## Personal setup

1. Create your own [Google Cloud project](https://console.cloud.google.com/) and enable Gmail API.
   A personal Google account can do this; Google Workspace policy may require administrator approval.
2. Configure Google Auth Platform branding and audience. For personal testing choose External / Testing
   and add your own Gmail account as a test user. Request only
   `https://www.googleapis.com/auth/gmail.readonly` under Data Access.
3. Copy [the static callback page](../examples/gmail/callback.html) to an HTTPS site you control,
   for example `https://your-domain.example/gmail/callback.html`. Serve the file as HTML. Do not use
   the GitHub source viewer URL. Use a dedicated page without analytics, third-party scripts, or
   injected host scripts. Disable query-string access logging where the host supports it, and set
   `Cache-Control: no-store` and `Referrer-Policy: no-referrer` response headers.
4. Create an OAuth client with application type **Web application**. Add the exact HTTPS page URL
   under Authorized redirect URIs, including path and trailing slash if any. No JavaScript origin is
   needed. Do not enter a `cherrystudio://` URL in the Google console.
5. In Cherry Studio → Plugins → Gmail, enter this client ID, client secret, and HTTPS callback URL.
   Sign in using your test account, approve read-only access, tap Continue on your callback page,
   then verify the mailbox shown in Cherry before connecting.

The page is user-hosted: Cherry does not provide a deployed OAuth relay. It receives only a
short-lived authorization code and state, strips the query from browser history, and links to one
of the fixed Cherry production/development/preview callback schemes. The app validates state and
exchanges the code with Google using S256 PKCE and the user's client credentials. Tokens and the
client secret stay in native secure storage; the callback page must never contain them. The client
secret in a native app is not a publisher-wide confidential secret. Use an application you own for
personal access; do not distribute one shared Web client secret with the open-source app.

## Google eligibility and limits

`gmail.readonly` is a **restricted** scope. Personal use and development/testing can qualify for
verification exceptions; this is not blanket exemption for a public service. External Testing is
limited to listed test users (up to 100), and Gmail refresh grants generally expire after seven days.
Reauthorize when required. Publishing the OAuth project can remove the testing-specific seven-day
expiry, but does not itself satisfy verification requirements or bypass unverified-app user caps.
A public distributed integration can require Google verification; server storage/transmission of
restricted data can additionally require a security assessment. Workspace Internal is available only
to eligible organizations and their users, subject to administrator policy.

The plugin renews access tokens during use and preserves Google's refresh token when no replacement
is returned. It offers Google revocation through the existing disconnect flow. Revocation can affect
other grants associated with the same Google application. You can also remove access in
[Google Account permissions](https://myaccount.google.com/permissions).

Large message bodies and threads are bounded and marked incomplete. Non-text attachments are
metadata only; unsupported body encodings are reported as incomplete. Gmail links may require
switching to the connected account. The plugin reads on demand and does not run background inbox sync.
